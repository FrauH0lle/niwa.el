    Float the composer as a second window on the view buffer¶

    Status: superseded by ADR 0136: Dock the composer in its own buffer. The child frame clipped completion and command popups; the composer now uses a window in the transcript's frame. The following record describes the former design, which amended ADR 0126.

    Former decision¶

    While the selected view window is scrolled away from the composer, a floating composer shows the same composer in a child frame over the bottom of that window, the host. It is a second window on the view buffer, not a copy and not a separate buffer: draft, rail, mode badge, keymaps and live progress are the view buffer's own. niwa-floating-composer (default on) turns it off; turning it off removes every floating composer and returns a cursor it held to the inline draft. Setting it with setq does the same at the view's next command.

    • Child frame over the host. The frame uses the note frame's shared child-frame parameters, without a border and with the theme's ordinary default background. It spans the host's full width, text area and both fringes, and sits flush on the host's text-area bottom; its window carries the host's fringe widths, so the draft stays aligned with transcript text. It is as tall as its top line plus the composer from the rail down, the latter capped at half the host's text height. The frame is created once per view, hidden between uses, and deleted with the view or when the option is turned off. Note-frame windows, historical segments and agent transcript views never have one.
    • Top line. The window's header line is drawn with the frame's own header-line face: an overline in the shadow foreground over the default background, one piece across the whole width, fringes included. On the left it shows ↑ N more in shadow while N draft lines of a capped draft are scrolled out above (counting costs nothing while none are); on the right a ↓ Back to bottom button (niwa-floating-composer-back-to-bottom, mouse-1) in a theme-derived tint of the background. Clicking it selects the host at the floating composer's draft position and scrolls the host so the buffer end shows on its last row (or, for a draft taller than the window, the cursor's line); the floating composer then hides by the rules below. The faces are set on the frame again only after a theme reset or changed them.
    • Terminal frames. In terminal Emacs it is a terminal child frame with the same behavior. Its geometry is in whole cells (a terminal's pixel is a cell). A terminal cannot draw an overline, so the top line fills the space between its texts with ─ characters. A terminal sends keystrokes to the selected child frame itself and select-frame never moves a redirect there, so a stale redirect would send the host's later keystrokes back to the floating composer: on a terminal hand-over selects the floating composer without redirecting its parent.
    • When. Only the selected window can be a host, and only while it shows neither its cursor's draft position nor a full line of the composer (rail or draft), so it hides as soon as the host fully shows the first line of a composer taller than the window. So it follows the selected window across splits, window selection and frame resizes, and hides while another frame, tab or buffer is selected; closing its parent frame deletes it.
    • Focus. The floating composer never takes compositor focus (no-accept-focus). Under PGTK a child frame that once held compositor focus never returns it to its parent (select-frame-set-input-focus on the parent does not, only deleting the child does), which left the view unattended: stream renders deferred and the rail stopped. Hand-over therefore selects the floating composer's window and redirects the host frame's keystrokes to it with redirect-frame-focus; hand-back clears the redirect and selects the host. Selecting another window from the floating composer, for example by clicking the host, retargets the redirect at the newly selected frame (select-frame does this for the frame holding compositor focus); clicking into the floating composer sets it. Removing the floating composer (view killed, option off) clears the redirect it set, wherever it points by then, unless another view floating over the same frame redirected it since: the frame records the last view to redirect it (niwa-floating-composer-owner). When the host window is deleted or shows another buffer, a window-buffer change hook, installed with the first floating composer and removed when the option goes off, clears the redirect in that redisplay, before the next keystroke, and a timer then deletes the orphaned floating composer.
    • Excluded from view geometry. The floating composer's window carries niwa-view-geometry-excluded, so niwa-view--windows' geometry answer omits it. Viewport capture and restoration (ADR 0126), composer anchoring, blank-space repair and narrowest-window chrome fitting (rail, panel rows, mail notices) ignore it, and its own resizes do not refit the host's rail. It starts at the rail instead of being anchored; a draft taller than the cap scrolls with its cursor, never above the rail.
    • Still counted for visibility. The rail is on screen in the floating composer, so animation visibility keeps counting its window, and its frame carries niwa-view-animate-as-parent so animation's frame choice treats it as its parent.
    • Slower rail animation in the floating composer. While every attended window showing the request label is a floating composer, the label animates at the battery frame-rate ceiling (niwa-view-spinner-battery-framerate, the rate the save power policy always applies), in the Lisp timer and in native presentation alike. The Lisp painter repaints the label only once its own period has passed, even when a pending-tool row wakes the shared timer sooner. When the rail is also visible inline, it runs at the normal rate. Pending-tool rows keep their rate. No option controls this: the user accepted the floating composer's typing cost and chose to slow, not stop, its animation (2026-11-19).
    • Placement cost. The composer's natural height is measured with a pixel limit of the top line, the cap and one more line (the limit counts from the window's top, header included) and cached until the buffer (buffer-modified-tick, so property changes such as a face height count), the window width, the face remapping (text scale) or a face or fontset definition changes (the generations the table layouts keep, which count global text scaling and a named face of the draft changing size), so scrolling the host measures nothing. The top line's ↑ N more count is kept on the same terms plus the window start. The top line's height is at least the parent's line height plus overline-margin: until the window is drawn, and after a font change until it is redrawn, Emacs reports an estimate from the font alone, without the overline's margin, and a frame sized by it is too short. Measuring fontifies the draft, which itself modifies the buffer, so the cache records the buffer's state after measuring; keyed before, every key measured twice. Overlay changes do not invalidate it. The key stores a copy of the face remapping, which face-remap-add-relative edits in place. A typed key still measures once before redisplay: a PGTK child frame's resize takes effect before the next redisplay, so measuring later would show the grown draft scrolled in the old height for a frame. Resize and move are one compound call, issued only when the requested geometry differs from the frame's own: restoring a window configuration, as leaving the minibuffer does, rounds the frame to whole lines. Creating the hidden frame and hiding it bind pgtk-wait-for-event-timeout to nil: PGTK otherwise runs its event loop for that whole timeout (0.1 s) on every hide. Updates run after the user's commands in the view and, coalesced into one timer, on the view's render cadence and window size, buffer and selection changes; the timer is not armed while the floating composer is hidden and the selected window's cursor is in the draft.

    Cursor and scrolling (amends ADR 0126)¶

    • When the user's scroll command in the selected window pushes its draft cursor off screen, the floating composer takes the cursor at the same draft offset. The offset is ADR 0126's pending return, captured before native scrolling displaced point; handing over consumes it, so a later inline return cannot overwrite edits made in the floating composer. The host's own point stays in the transcript: it remains a history reader.
    • A cursor in the transcript stays there; the floating composer is shown without taking it.
    • A scroll command after which the floating composer's cursor position is fully visible in the host hides the floating composer and returns the cursor there, so a draft taller than the window can return too.
    • Only post-command-hook moves the cursor. Timers, window hooks, streaming and other background updates only place, show or hide a floating composer that is not selected. Settling a card visited with C-c C-j is the one exception, described below.
    • C-c C-j from the floating composer moves the cursor to the host first, so the visit and the draft offset it remembers belong to the host, and selects the card there. While a floating composer is shown over the window, a card whose cursor line would be hidden behind it is scrolled to the window's top, or, if the card is too tall for that, its cursor line just above the floating composer. Arriving cards move nothing.
    • Settling the visited card, while the host still visits it, returns the cursor to the remembered draft offset: inline when the host fully shows that position, otherwise in the shown floating composer, leaving the host's point in the transcript.
    • Sending with C-c RET from the floating composer needs no rule of its own: the host's point is in the transcript, so ADR 0126 keeps its viewport as a history reader, and the cursor stays in the emptied floating composer. Input typed while the submission is prepared is kept as inline.
    • With the option off ADR 0126's per-window return-to-draft is unchanged.

    Keys and pointer¶

    Keys act on the selected window; with the cursor in the transcript they keep their transcript meaning (n, p, t, TAB, RET).

    • C-c C-SPC (niwa-floating-composer-toggle) moves the cursor between the composer and the transcript: between the floating composer and its host while it is shown, else between the inline draft and the transcript, each toggle returning to where the previous one left the window's cursor. Clicking the floating composer selects it as the toggle does.
    • In the floating composer C-v and M-v page within a capped draft. After every command, and whenever redisplay finds it scrolled above the rail (touchpad momentum scrolls within one command), its window start is clamped to the rail, so neither these keys nor the wheel ever show transcript text in it; an uncapped draft stays pinned at the rail. Redisplay scrolling it down to show point in a frame still too short is left alone: pinning that back made redisplay scroll again without end; a size change of its window schedules a refit instead. Scrolling below the draft's end shows blank space, as in any window.
    • C-M-v/C-M-S-v there scroll the host: the view sets other-window-scroll-default buffer-locally to return the host from the floating composer and defer to the global default elsewhere.
    • The wheel scrolls the window under the pointer (mouse-wheel-follow-mouse) and leaves the selection, and so any keystroke redirect, where it was.
    • C-x 2/C-x 3 there split the host: the floating composer's window carries a split-window parameter that splits the host instead. The cursor stays in the floating composer.

    Rationale and consequences¶

    Problem: while writing a prompt the user often needs to look something up in the transcript, and had to scroll back and forth.

    Redisplay cost (from the Emacs C source, 30.2 and 32.0.50 trees; measured by the performance gate below): a buffer change flags every window showing the buffer for its next redisplay, where each is updated incrementally; windows showing only other buffers are normally skipped. Several changes before one redisplay coalesce. The floating composer therefore adds an incremental update of its window to redisplays that follow typing or streaming, only while it is shown. Without the geometry exclusion it would also add a full anchoring pass per stream update (about 1 ms each in ADR 0126's measurements).

    The rail is fitted to the host; the floating composer has the host's text width, and its measured height includes any wrap. Since its width follows only the host there is no resize loop.

    Performance gate against "off"¶

    The floating composer performance gate (see the development guide) first ran on the integration tree at b9cb7956 (2026-11-19) and did not reach parity. Its findings had these causes, now removed:

    • Focus loss after the cursor returned inline, which left the view unattended (renders deferred, rail stopped): PGTK child-frame focus, see "Focus" above. The graphical ERT suite stubbed frame-focus-state and could not see it; it now runs with real compositor focus.
    • A constant +100 ms on scrolling back (105 vs 5 ms): PGTK's make-frame-invisible always runs GTK's event loop for the whole pgtk-wait-for-event-timeout. Creating the hidden frame paid the same wait, 100 of the 157 ms first show.
    • Per-keystroke height measurement: the measurement's own fontification modified the buffer after the cache key was taken, so the next update measured again: every key measured twice.
    • Idle CPU with a floating-composer frame: the benchmark scanned every process inside its measured interval, summed per-thread CPU so an exiting thread made it smaller, and its "unfocused" frame showed the view itself. The benchmark now measures per-thread deltas outside the scan, and the unfocused frame shows another buffer. The earlier idle numbers are not comparable with those below.

    Final run, on the complete feature (integration tree at 74a0a1e9, 2026-11-19): Emacs 31.1 pgtk, byte-compiled, private presenting KWin (virtual, OpenGL, no lock screen); presentation probes before and after with 73 and 67 completed frame callbacks; one warm-up round and 6 alternating rounds; every measured workload began focused and attended except idle-unfocused, which is unattended by design and measured before any crossing, so on-never has never created a frame. The power policy is pinned to full, so only the floating composer's rule applies the battery ceiling (15 fps); earlier runs left it at auto, which in the private session animated every rail at the ceiling (off-inline idle with a request: 86-92 ms Emacs CPU and 20-21 redisplay cycles per 4 s under auto, 142 ms and 36 under full). Crossings count each direction's commands separately; their CPU includes the benchmark reading per-thread CPU before each command, equally in every scenario. Values are scenario vs baseline; "paired" is the per-round difference, median [min, max] over 6 rounds. No parity verdict is recorded here. A repeat of the whole gate at 34da91d5 measured no cost clearly above these: medians above a range here were inconclusive (quiet-idle CPU under 1 ms, stream redisplay cycles with ranges spanning zero), and the visible floating composer measured less (typing ratio 1.34 [1.26, 1.77], Emacs CPU +33 [+26, +89] ms; wrapped deletion +29 [+15, +84] ms; stream against the hidden rail +169 [+167, +226] ms). The second run, before keys, long drafts, C-c C-j, window handling and terminal support landed, measured the same within these ranges except where noted.

    Remaining regressions other than visible rail animation:

    • Typing in the visible floating composer (on-visible vs off-inline, 40 keys per run): latency including redisplay 2.56 vs 1.52 ms median (pooled, n 240 each), per-round ratio 1.62 [1.42, 1.74]; Emacs CPU +65 [+39, +86] ms per run. A probe in the second run split this: with the floating composer's update disabled, keys still cost 1.88-2.40 ms against 1.36-1.82 ms inline (run medians, 4 alternating runs of 40 keys), so most of it is redisplaying the second window; the one remaining measurement per key takes about 0.06 ms of layout. The user accepted this cost (2026-11-19).
    • Wrapped-draft deletion in the visible floating composer (30 keys per run): Emacs CPU +46 [+34, +55] ms per run and one more GC (+1 [+1, +1]); latency is lower, 3.56 vs 4.15 ms median (n 180 each), ratio 0.87 [0.83, 0.98].
    • Unfocused idle with a floating-composer frame that exists (4 s, the view's frame unfocused): on-hidden Emacs CPU +6.5 [-0.4, +18.8] ms and redisplay cycles +1 [+0, +8]; on-visible +3.5 [-3.9, +16.7] ms and +1 [+0, +8]. The CPU differences are inconclusive; the never-created control on-never also measured +2.6 [-6.3, +14.3] ms with +1 [-1, +7] redisplay cycles. A probe found an extra redisplay with no Lisp timer due, about 0.9 and 1.4 s after focus left, so the frame's window-system events drive it.
    • First show, which creates the child frame once per view: 50.72 ms median, p90 61.85 ms (n 36), no "off" counterpart, with 2 child-frame move/resize calls each. Without PGTK's wait this is frame creation itself.

    Visible rail animation, with the rail visible only in the floating composer and so animating at the battery ceiling:

    • Idle with a request, against the hidden rail (on-visible vs off-away, 4 s): Emacs CPU +88.8 [+80.4, +95.3] ms, KWin CPU +27.9 [+19.4, +32.1] ms, redisplay cycles +19 [+18, +19].
    • Idle with a request, against the rail visible inline at the normal rate (off-inline): Emacs CPU -47.5 [-57.1, -28.7] ms, KWin CPU -19.7 [-33.1, -4.9] ms, redisplay cycles -14 [-14, -13].
    • Stream, 100 chunks at 40 ms, against the hidden rail: Emacs CPU +227.9 [+173.5, +273.1] ms, KWin CPU +28.8 [+6.1, +56.5] ms, redisplay cycles +41 [+40, +43], one more GC. Against the inline rail: Emacs CPU -15.3 [-75.9, +38.8] ms (inconclusive), KWin CPU -1.0 [-37.4, +34.6] ms, redisplay cycles -5 [-9, -4].

    No regression measured:

    • Scroll away (on-never vs off-inline, 12 crossings per run, n 72 each): 6.05 vs 7.69 ms median, ratio 0.78 [0.76, 0.83]; Emacs CPU -39 [-45, -27] ms and redisplay cycles -1 [-2, -1] per run; KWin CPU -0.1 [-1.8, +2.6] ms (the second run's +1.5 ms is gone).

    • Streaming with the floating composer hidden (on-hidden): Emacs CPU +25.7 [-44.8, +75.3] ms and KWin CPU +4.9 [-18.7, +25.3] ms per 100 chunks, both inconclusive (the second run measured KWin +10.7 [+3.1, +13.6] ms); on-never +28.6 [-60.7, +82.7] and +3.3 [-13.3, +42.7] ms.
    • On but never created (on-never vs off-inline): wrapped deletion 4.28 vs 4.15 ms median, per-round ratio 1.05 [1.01, 1.08], higher in every round of this run only; a repeat of the whole gate at 34da91d5 measured ratio 0.94 [0.89, 1.12] (rounds 1-5 quiet, round 6 under an unrelated test suite), and isolated per-merge runs and a key-interleaved control straddled zero. Typing 1.70 vs 1.52 ms, ratio 1.03 [0.93, 1.17] (repeat: 0.95 [0.78, 1.17]). Idle with a request +3.6 [-8.5, +23.8] ms; quiet idle +0.1 [-0.2, +0.4] ms.
    • Hidden after use (on-hidden vs off-inline): typing 1.42 vs 1.52 ms; wrapped deletion 3.61 vs 4.15 ms; idle with a request -0.7 [-7.2, +9.6] ms; quiet idle +0.3 [-0.3, +1.0] ms.
    • Visible floating composer, quiet idle: Emacs CPU +0.3 [-1.2, +0.7] ms.
    • Child-frame move/resize calls were 0 in every paired workload (the draft height did not change); show/hide were 1 per crossing direction.

    Rerun with the full-width frame and top line¶

    Run on the tree at ecef42ff (2026-11-19), after the full-width frame and top line replaced the inset, bordered one: Emacs 31.1 pgtk, byte-compiled, private presenting KWin; presentation probes before and after with 68 and 66 completed frame callbacks; one warm-up round and 6 alternating rounds; power policy pinned to full. Values and statistics as above (scenario vs baseline; paired median [min, max] over 6 rounds); the earlier run's value follows in parentheses.

    Crossing and first-show CPU, KWin and redisplay totals are whole-transition numbers, not per notch. A scroll-away total covers every notch up to the crossing and the settling between them; a scroll-back total likewise covers all its notches, starting from the viewport the scroll-away left; a first-show total also covers removing the frame, the return crossing and the settling around them. Their latencies time only the crossing notch.

    • Typing in the visible floating composer (on-visible vs off-inline, 40 keys per run): latency 2.50 vs 1.72 ms median (n 240 each), per-round ratio 1.51 [1.41, 1.67] (1.62 [1.42, 1.74]); Emacs CPU +56 [+38, +64] ms per run (+65 [+39, +86]).
    • Wrapped-draft deletion, visible (30 keys per run): Emacs CPU +46 [+36, +50] ms (+46 [+34, +55]); latency 3.76 vs 4.26 ms median, ratio 0.88 [0.82, 0.89] (0.87 [0.83, 0.98]).
    • One child-frame refit per visible session: typing and wrapped deletion each count one move/resize call per run (the earlier run: 0), not one per key. The cause is unverified; a likely one is that the top line's ↑/↓ come from a fallback font a pixel taller than the default, so the drawn top line is taller than the height computed before drawing and the size change refits the frame once.
    • Scroll back (on-never vs off-inline, 12 crossings per run, n 72 each): 2.83 vs 6.12 ms median, ratio 0.47 [0.43, 0.49] (0.56 [0.52, 0.58]); Emacs CPU +74 [+36, +117] ms, redisplay cycles +46 [+45, +47] per run.
    • Scroll away is not comparable with earlier runs: 8.74 vs 7.83 ms median, ratio 1.12 [1.09, 1.16]; Emacs CPU +205 [+187, +220] ms, KWin CPU +17 [+13, +27] ms, redisplay cycles +51 [+49, +51] per run. Since the floating composer appears only once the host shows no composer line (19fbf2c8), one wheel notch no longer always hands the cursor over and the benchmark stopped at its first crossing; ecef42ff makes it scroll away notch by notch, as scrolling back already did, and report the crossing notch's latency. With the option on a crossing now takes an extra notch whose CPU and redisplay cycles the whole-transition totals count, while off leaves the draft after one.
    • Idle with a request, visible, against the hidden rail (off-away, 4 s): Emacs CPU +87.7 [+80.5, +109.3] ms (+88.8 [+80.4, +95.3]), KWin CPU +21.8 [+18.7, +29.2] ms, redisplay cycles +19 [+18, +20]. Against the rail visible inline: Emacs CPU -54.2 [-57.8, -37.0] ms (-47.5).
    • Quiet idle, visible: Emacs CPU -0.39 [-0.86, +0.05] ms (+0.3 [-1.2, +0.7]).
    • Unfocused idle, visible (vs off-inline): Emacs CPU -2.5 [-10.2, +28.7] ms, inconclusive (+3.5 [-3.9, +16.7]).
    • Stream, visible, against the hidden rail: Emacs CPU +188.5 [+171.6, +226.8] ms (+227.9 [+173.5, +273.1]), redisplay cycles +40 [+37, +43].
    • First show: latency of the crossing notch 55.81 ms median, p90 62.81 ms (n 36) (50.72, p90 61.85).

    Alternatives¶

    • Docked window below the transcript. Covers nothing, but shrinks the transcript window whenever it appears, reflowing the transcript and firing size hooks across the view; it costs the same extra window redisplay. The child frame was chosen then; ADR 0136 later adopted an ordinary split with a separate composer buffer.
    • Inline composer with a jump key. No extra cost, but the user cannot see the draft and the passage being looked up together. Rejected.
    • Separate composer buffer. Initially deferred because migrating the inline input marker and viewport rules was a larger change. It was the only variant expected to stop draft edits and streamed output from invalidating the same buffer's windows. ADR 0136 adopted it after the child frame could not reliably host native editing popups.

    Decision history¶

    • The inset, bordered frame was replaced by a full-width frame under a top rule (2026-11-19). The floating composer was first inset two columns from each side of the host's text area, floated half a line above its bottom and wore the note frame's teal border, active or inactive by focus (on a terminal, box characters in the frame's own border face). The inset left clipped transcript fragments visible around the frame. After comparing Claude Code and Codex with a prototype, the user chose the full-width, flush frame with a rule, ↑ N more and a "Back to bottom" button; the border painting and its focus colors were removed. The rule is the header face's overline because the prototype's stretched strike-through segments broke at the fringes.
